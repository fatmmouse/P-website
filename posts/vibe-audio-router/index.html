II 自己 几点睡，谁说了算？ 长文

耳机里的音乐为什么会变闷：一次 Mac 音频路由的小工程

harry 写 2026 年 7 月 3 日 约 7 分钟 纯文本版

戴蓝牙耳机听歌时一按语音输入，音乐突然变闷——这不是 App 的 bug，而是蓝牙协议的硬限制。从这个怪象出发，查清根因，用 Hammerspoon 写了个自动音频路由，并把私人配置打磨成了开源项目。

这是我做 vibe-audio-router 这个开源小工具的完整记录。从一个「耳机音乐莫名变闷」的怪象，到查清蓝牙协议的根因，再到一步步踩坑解决。写下来既是复盘，也想给同样 Vibe Coding 的人省点时间。它也代表了我捣鼓东西的方式：从「为什么」出发，不放过任何一个不对劲的细节。

harry 自己写在前面的话

一、怪象

某天我戴着蓝牙耳机，边听歌边 Vibe Coding——用语音输入对着电脑说需求。话音刚落，耳机里的音乐突然变闷了，像被罩上一层布。

音量没动，均衡器没动，歌还是那首歌。但我能听出来：变差了。

我反复试，规律很清楚：一按语音输入键，音乐就变闷；过一会儿，又恢复。这不是偶发，是必然。

第一反应是：语音输入软件偷偷改了我的音效？毕竟它是个 App，App 干预音频不算稀奇。

这个判断错了。但正是这个错误的判断，让我后来排查时格外谨慎，不再轻易归罪于某个 App——也让我多花了些时间，才走到正确的方向。

二、真凶是蓝牙协议，不是 App

要搞清楚”谁动了音频”，最直接的办法是换输出设备。我把输出从耳机切到电脑自带扬声器，再按语音输入键——扬声器一切正常，没有变闷。

所以问题只在耳机上。

接着我盯着 macOS 的声音设置看，发现了线索：按下语音输入的那一刻，系统的「声音输入设备」从外接领夹麦跳到了耳机自带的麦。

顺着这条线搜，真凶浮出水面——它叫 A2DP 和 HFP。

蓝牙耳机在 Mac 上有两个工作模式。一个是 A2DP，专门用来传高质量音频，立体声、高采样率，但只能单向播放，用不了麦克风。另一个是 HFP（免提协议），双向，能同时录音和播放，但音质被刻意压到通话级别——单声道、窄带宽、采样率掉到 16kHz。

关键在于：耳机的麦克风只有在 HFP 模式下才能用。而 Mac 一旦激活耳机的麦克风，就等于强迫耳机从 A2DP 切到 HFP，输出音质立刻塌方。1

这不是语音输入软件的锅，也不是音量能救的，是蓝牙协议写死的规则。

我之所以一开始怀疑软件，是因为把”现象”和”原因”搞混了——变闷是输出端的表象，但开关在输入端：是「输入设备被切成了耳机麦」这一步，触发了模式切换。排查问题的第一课：盯着实际变化的那个变量，而不是最先引起你注意的那个。

三、手动切的死路

知道原理后，解法似乎很简单：语音输入时别用耳机麦，用我那个外接的领夹麦（DJI Mic Mini）。

于是我开始手动操作——每次按语音输入前，钻进系统设置，把输入设备切到领夹麦。

试了一天就放弃了。一天切十几次，而且经常忘，忘了就又变闷。更要命的是，切过去之后，如果我想用别的软件录音（比如开个会议），又得切回来。我发现自己在一个三步的循环里反复横跳：切、用、切回。

人不应伺候机器。这种重复，正是该被自动化的对象。

四、换个角度：不绑按键，绑状态

第一版我本能地想：能不能在「按下语音输入键」的那个瞬间，自动切麦？

但这个思路有个前提——得先劫持那个按键。而语音输入键是系统级的，劫持它既复杂又脆弱，还可能和别的软件打架。

我把问题重新讲了一遍：我真正要的，到底是什么？

不是「按下键时切麦」。我真正要的是：Mac 永远用当前手里最好的那个麦克风。

领夹麦在线，就用领夹麦；领夹麦不在，就用耳机麦；耳机也不在，就用电脑内置麦。语音输入软件读取的是「系统默认输入设备」，那只要保证这个默认值始终是对的，按下键的那一刻自然就用对了——根本不需要去劫持按键。

这是这次折腾里最关键的一次转向。从「响应一个动作」退回到「维护一个不变的状态」，问题瞬间简单了一半。很多时候，把需求从「我想在 X 时做 Y」改写成「我想让 Z 始终为真」，解法会自己浮现。

五、Hammerspoon 与三个坑

我选了 Hammerspoon，一个 macOS 上的自动化工具，用 Lua 写配置。核心逻辑只用了它的两个能力：监听音频设备的增删，和切换默认输入设备。设备一变化，就去检查一遍”现在该用哪个麦”，然后切过去。

主线逻辑一个晚上就跑通了。但真正花时间的，是后面三个坑。

第一个坑：领夹麦会反过来劫持输出。

我的领夹麦是蓝牙的，它在系统里同时占了一个输入端点和一个输出端点——那个输出端点是给录音时监听用的，单声道、16kHz。问题来了：macOS 有个讨厌的习惯，蓝牙设备一连上，它爱把输出也顺手切过去。于是每当领夹麦连上，我的输出就被劫持到那个监听通道，听歌变得又干又窄。

输入是我主动要切的，但输出我只想钉在耳机上。所以路由逻辑要分两半：输入按优先级选最优，输出则只做”保护”——一旦发现输出被领夹麦抢走，立刻拉回耳机。

第二个坑：合盖断蓝牙，顺手废掉了解锁工具。

我很早就写了一段「合盖自动断开耳机」的逻辑，用的是最常见的做法：合盖时直接关掉整个蓝牙。

直到有一天我发现，我另一个依赖蓝牙的软件——BLE Unlock，靠检测手机离电脑的远近来自动锁屏、解锁——突然不好使了。原因显而易见：蓝牙都被我关了，它拿什么检测信号？

这是我应该早点想到的。一个改动波及的不只是眼前这个功能，还有所有共享同一资源的其他功能。正确的做法不是”关蓝牙”，而是”只断开耳机这一条连接”——蓝牙本身始终保持开启。改完之后，耳机照样合盖断开，BLE Unlock 也恢复正常。

第三个坑：重启之后的设备重连顺序。

测试时我发现，重启之后音频路由偶尔会落在一个奇怪的状态——比如输出停在内置扬声器，没切回耳机。排查后发现是时序问题：重启后蓝牙设备不是一个一个整齐连上的，耳机和领夹麦谁先到不固定。如果领夹麦先连上，输出被它劫持，而此时耳机还没上线，逻辑只能把输出暂落到内置扬声器；等耳机随后连上，路由却没有再触发一次。

解法是给整个逻辑加上”重连后兜底再跑一次”的机制，并在设备变化时做一点去抖——等几个设备都连稳了，再做一次最终决策。

这三个坑，没有一个是写第一版时能预见到的。它们都是在实际使用、实际出错的过程中，一个一个被撞出来、再被修掉的。这也是我越来越相信的一件事：没有真正”用起来”的工具，就不算做完。

六、把它变成开源项目

整套配置稳定跑了一阵之后，我意识到一件事：这个痛点不是只有我一个人有。

现在用语音输入写代码的人越来越多，外接一个领夹麦 + 戴蓝牙耳机几乎是标配，而”一按语音输入音乐就变闷”这个现象，凡是这个配置的人都撞过——只是大多数人以为是玄学，忍了。

于是我把这套私人配置重新整理成了一个开源项目：把硬编码的设备名抽出来做成一个配置区，写了个脚本帮别人一键查出自己 Mac 上的设备名和蓝牙地址，配上 README 和一篇讲清原理的文档。别人 clone 下来，填几行自己的设备信息，就能用。

项目地址：https://github.com/fatmmouse/vibe-audio-router

七、几点收获

回看这次折腾，有几件事比”解决了一个音频问题”本身更值钱。

第一，盯着那个真正在变的变量。耳机变闷是输出端的表象，但开关在输入端。归因归错了层，再怎么折腾输出都白费。

第二，把”响应动作”改写成”维护状态”。这是这次最关键的一次思路转向，也是我后来反复用到的方法——很多看似需要复杂触发逻辑的需求，本质只是想让某个东西”始终是对的”。

第三，改动要看它波及的整个面。关一个蓝牙，废掉一个解锁工具。任何共享资源的改动，都要问一句：还有谁在用它？

第四，没有用起来的工具不算做完。第一版能跑和真正稳定之间，隔着三个只有实际使用才会暴露的坑。

最后，把私人方案打磨成公共工具，是对一个问题的最终验收。当你能把一个只为自己而做的方案，重新组织到陌生人也能 5 分钟上手，你对这个问题的理解才算是真正吃透了。
